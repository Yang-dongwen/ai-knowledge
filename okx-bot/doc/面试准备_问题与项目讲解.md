## 4. 项目深挖问答

### 4.1 AI 智能内容工具台

#### Q1：为什么要做这个项目？和「调一下 OpenAI API」有什么区别？

**答：**  
调 API 只解决「模型会不会答」。业务系统要解决：谁能用、任务多久跑完、失败怎么重试/暂停、进度怎么推、模型换了代码改多少、会不会被 SSRF 打穿、会不会串号看到别人数据。  
我做的是后面这一整套：**鉴权会员 + 异步任务状态机 + 调度限流 + Port-Adapter + SSE + 安全**。

#### Q2：任务状态机怎么设计的？为什么要调度槽位？

**答：**  
典型状态：`PENDING → 运行中各阶段 → SUCCESS / FAILED / PAUSED`。不同工具阶段名不同（如下载、转写、总结、渲染），但模式统一。  
调度槽位是全局并发上限（例如同时只跑有限个重任务）。因为 LLM、ASR、渲染都贵且慢，如果请求来多少跑多少，会把机器和供应商配额打爆，也会让所有任务一起变慢。  
**槽位 = 用吞吐换稳定**，是 AI 任务系统的基本功。

#### Q3：LangChain4j 和 OkHttp 双实现怎么做？为什么要可回滚？

**答：**  
业务只依赖统一的 Chat 出口（如 `LlmChatClient`），下面两个 Adapter：一个走 LangChain4j，一个手写 OkHttp 调 OpenAI 兼容协议。用配置项切换。  
原因：引入新框架有兼容/超时/流式细节风险；双实现可以灰度，出问题一键回 OkHttp，**业务流水线不用改**。Chat 文本和 FLUX 生图协议也分开，避免硬套。

#### Q4：什么是 Port-Adapter？举个你项目里的例子。

**答：**  
Port 是业务定义的接口（「我要一张图」「我要分镜 JSON」），Adapter 是对接具体厂商的实现。  
例如文生图：`ImageGenPort` → `NvidiaFluxImageAdapter`；以后换别的厂商只加 Adapter，流水线不变。  
抓取、渲染同理。这是六边形架构的务实用法，目的是**变化隔离在边界**。

#### Q5：SSE 和 WebSocket 你为什么选 SSE？

**答：**  
任务进度和聊天流式以**服务端推送文本事件**为主，客户端以接收为主，SSE 足够，实现和代理兼容通常更简单。  
真取消可以配合服务端注册表中断生成。若以后要强双向（客户端频繁上行控制），再评估 WebSocket。

#### Q6：视频提取流水线失败了怎么处理？长视频怎么办？

**答：**  
阶段失败进入 FAILED，保留错误信息；支持暂停等状态。长视频避免简单头尾截断导致中间信息丢失，用分层摘要/分段策略；理解模式可配置 audio-only / hybrid，控制成本和质量。  
（按你实现细节补充：重试是否整管线、是否断点续跑。）

#### Q7：文章抓取的 SSRF 怎么防？

**答：**  
用户提交任意 URL 时，服务端若直接请求，可能被导向内网（如 127.0.0.1、云元数据地址）造成攻击。  
做法包括：协议与端口限制、解析 DNS 后校验目标 IP 非私网/保留地址、DNS 钉扎（请求打到已校验的 IP）、超时与大小限制。  
强反爬平台不硬刚，提供**粘贴正文降级**，保证产品可用且合规风险可控。

#### Q8：Agent 里为什么写操作要确认？

**答：**  
模型会幻觉。如果自然语言直接「删除/批量创建任务」而不确认，误操作成本高。  
所以 Tool 分查询与写入；写入先出确认卡，用户确认后再执行，并且全程带 `userId`，禁止越权。

#### Q9：这个项目有真实用户/营收吗？

**答（诚实版）：**  
目前以独立产品工程验证和持续迭代为主，重点交付的是**可运行的架构与模块完整度**（鉴权、多工具、文档与单测）。若面试官追问数据，不编造 DAU；可强调下一步是完善支付进件、配额与部署。  
**价值主张放在工程能力可迁移到公司业务。**

#### Q10：代码量 350+ 文件，你怎么保证质量？

**答：**  
模块边界清晰（video/aigen/imggen/article/auth…）；关键路径有单测（URL 安全、适配器、状态等）；设计文档写清决策与验收；配置外置；LLM 出口可回滚降低集成风险。

### 4.2 EnvManage

#### Q11：资源占用锁具体怎么做的？分布式吗？

**答：**  
业务上要保证设备不能被两个任务同时占用。实现上在占用/释放路径加互斥（按你实际：DB 乐观锁/状态机条件更新、或 Redis 锁、或二者结合）。  
面试时讲清三点：  
1. **临界区**是什么（占用状态变更）；  
2. **失败怎么返回**（已被占用）；  
3. **异常释放**（超时、任务失败是否归还）。  
若只用了单机锁而部署多实例，要主动说明局限与改进（分布式锁/DB 条件更新）。

#### Q12：百万级 Excel 导出为什么内存能 < 50MB？

**答：**  
传统 XSSF 整表进内存会 OOM。SXSSF 是滑动窗口流式写盘；查询侧分页拉数据，而不是一次 select 百万行；HTTP 用 chunked 边写边刷。  
三者结合后，内存近似「页大小 + 窗口」，而不是「全表」。  
结果：内存约 < 50MB，响应约 3 秒级，业务处理效率提升约 60%。

#### Q13：HiTest 同步 30 分钟到 5 分钟，你做了什么？

**答：**  
全量同步每次拉全量设备数据，数据大、耗时长。改为**增量同步**（按时间戳/版本/变更集，按你实际字段说），只处理变化部分；再配合任务拆分与缓存。  
收益主要来自**减少无效数据传输与写入**，而不是单纯加机器。

#### Q14：为什么用 LMAX Disruptor？和线程池比呢？

**答：**  
监控场景是生产者（采集/定时任务）持续产生事件，需要低延迟并行消费。Disruptor 是环形队列 + 无锁设计，适合这种**高吞吐事件处理**。  
线程池更通用，但在超高频事件路上队列与锁竞争可能成为瓶颈。我们用在监控异步并行路径，目标是响应 < 500ms 量级。  
（若面试官很深，承认：业务量级未必打满 Disruptor 极限，但选型解决的是异步解耦与并行处理结构。）

#### Q15：适配器模式在集成里怎么体现？

**答：**  
LCM、HiTest 接口不同。业务服务依赖统一的「设备申请/同步」抽象，具体 HTTP 调用、URL、字段映射在 Adapter 里；URL 可配置。  
好处：外部系统变更时改适配层，核心领域逻辑稳定。

#### Q16：5000+ 设备、99.9% 可用性，你个人贡献边界？

**答：**  
平台级数字是团队/产品结果；我的贡献要落到**主导模块与可验证优化**（导出、同步、占用、监控链路、底座能力）。  
不把整个平台可用性都说成自己一人保证，但可以说：模块设计考虑失败降级、缓存、异步解耦，支撑稳定性目标。

### 4.3 AIFactory

#### Q17：分库分表怎么分的？中间件？

**答：**  
按语料类型（图/视/音/多模态等）与数据规模做分片策略，结合 ShardingSphere；查询慢主要来自大表扫描与索引不当，分表后单表更小，再优化 SQL/索引，RT 从约 3s 到 200ms。  
追问准备：分片键是什么、跨片查询怎么避免、分页深度问题。

#### Q18：Kafka 在标注流水线里扮演什么角色？

**答：**  
上传/待标注事件进 Topic，消费者调不同标注模型，生产者与消费者解耦，可水平扩展消费能力，避免同步 HTTP 打爆模型和拖垮上传接口。

#### Q19：任务重跑如何保证数据一致性？

**答：**  
重跑会产生重复结果。我们按 `corpusId + indicatorId` 去重，保留最新记录（如 LinkedHashMap 顺序策略或 DB 唯一键/覆盖写）；批量写减少 IO。  
目标是：**可重跑、结果可解释、不脏读一堆历史分。**

#### Q20：大文件 10 万+ 上传如何控内存？

**答：**  
分片上传 + 流式读写，不把全部文件一次性读进 JVM；控制并行度；落对象存储/盘后只保留元数据在 DB。

### 4.4 天珑 BPM

#### Q21：BPMN 并行网关、条件分支怎么理解？

**答：**  
条件分支按表达式走不同路径；并行网关多条分支同时进行，汇聚后再往下。审批流里常见「会签/并行部门审批后再汇总」。

#### Q22：和 SAP 等系统对接注意什么？

**答：**  
数据模型不一致要用适配/转换层；注意事务边界（对方失败是否回滚本地）；接口超时与重试；主数据以谁为准。我们做实时同步时重点保证字段映射正确和失败可查。

## 5. Java / 基础技术问答

#### Q23：HashMap 和 ConcurrentHashMap？

**答：**  
HashMap 非线程安全；ConcurrentHashMap 用分段思想/CAS+synchronized（JDK8）保证并发读写安全。缓存、统计等高并发共享 Map 用 CHM。  
（可联系：本地缓存、计数、任务注册表。）

#### Q24：线程池参数怎么设？

**答：**  
核心参数：core、max、queue、reject、keepAlive、threadFactory。  
IO 密集（调 LLM、下载）可增大线程、队列要有界防 OOM；CPU 密集靠近 CPU 核数。  
拒绝策略按业务：调用方感知用 Abort + 友好错误；不能丢可用 CallerRuns 降速。  
**AI 任务**更倾向「有界队列 + 明确拒绝/排队中状态」，而不是无界队列。

#### Q25：CompletableFuture 用过吗？

**答：**  
AIFactory 异步生成 PDF 报告：提交计算任务并行执行，allOf 汇总，避免同步接口长时间阻塞，吞吐大约提升 3 倍。  
注意：自定义线程池，避免用默认 commonPool 打满；异常要用 exceptionally/handle 处理。

#### Q26：CountDownLatch 在你项目里怎么用？

**答：**  
多步异步任务需要「全部完成再进入下一步」时，主流程 await，子任务 countDown。EnvManage 多步流程完整性用过这类同步工具。  
与 CF 区别：Latch 更偏一次性等待计数；CF 更偏组合异步结果。

#### Q27：Spring Bean 循环依赖？

**答：**  
单例 setter/字段注入时三级缓存可缓解；构造器注入循环会失败，说明设计耦合，应拆模块或引入事件/接口。  
实际更建议从设计上消除循环。

#### Q28：事务失效场景？

**答：**  
同类自调用不走代理；异常被吞；非 public；错误的传播级别；多线程里子线程无事务上下文等。

#### Q29：Java 8 和 17 你用过哪些差异？

**答：**  
企业项目多 Java 8；独立项目 Java 17 + Spring Boot 3（Jakarta 命名空间）。  
17 有 records、text blocks、更强的 GC/性能与长期支持。迁移要注意 `javax.*` → `jakarta.*` 与依赖升级。

## 6. 数据库 / 缓存 / 消息队列

#### Q30：如何排查慢 SQL？

**答：**  
慢查询日志 → explain 看 type/rows/额外 filesort；补合适索引；避免 select *；大分页改游标；必要时分表。  
语料查询优化是分表 + SQL/索引组合拳。

#### Q31：索引失效常见原因？

**答：**  
对索引列运算/函数；隐式类型转换；前导模糊 like；最左前缀不匹配；or 一侧无索引等。

#### Q32：Redis 一般缓存什么？穿透/击穿/雪崩？

**答：**  
设备状态、热点配置、会话相关数据等。  
穿透：布隆/缓存空值；击穿：互斥锁或逻辑过期；雪崩：过期时间打散 + 多级缓存 + 限流。

#### Q33：Kafka 和 RocketMQ 怎么选？（结合你简历）

**答：**  
我在 AIFactory 用 Spring Kafka 做标注解耦，适合日志/流式/高吞吐事件。RocketMQ 在国内业务消息、延时消息等场景常见。  
选型看团队生态、消息语义、运维成熟度；我具备消息驱动拆分同步链路的实践。

#### Q34：消息丢失/重复怎么处理？

**答：**  
丢失：生产者确认、副本、消费者提交位点时机。  
重复：消费者幂等（唯一键、去重表、业务状态机）。  
标注/评测重跑场景我们按业务键去重保留最新。

## 7. 微服务 / 工程化 / 安全

#### Q35：微服务 0 到 1 你做了哪些？

**答：**  
日志与全局异常、多环境配置、敏感配置加密（Jasypt）、Flyway 迁移、CI/CD、（网关/注册视项目）、统一返回与基础组件，让业务模块可快速接入。

#### Q36：Gateway 的作用？

**答：**  
统一入口、路由、鉴权、限流、灰度。AIFactory 侧有 Gateway 统一接口调用相关实践。

#### Q37：JWT 优缺点？怎么做注销？

**答：**  
无状态、易扩展；缺点是注销难、载荷不宜太大。  
注销可用：短过期 + 刷新令牌；黑名单（Redis）；版本号/密码变更使旧 token 失效。  
我独立项目用 Spring Security + JWT + BCrypt + 邮箱验证码。

#### Q38：BCrypt 为什么比 MD5 好？

**答：**  
BCrypt 自适应耗时、自带 salt，抗彩虹表与暴力；MD5 快且不该用于密码。

#### Q39：配置加密、密钥怎么管理？

**答：**  
Jasypt 等加密配置文件敏感项；生产密钥走环境变量/密钥服务，不进仓库。独立项目同样密钥外置。

## 8. AI 应用后端专项

#### Q40：LLM 结构化输出怎么保证？

**答：**  
Prompt 明确 JSON schema；用模型 JSON mode（若支持）；服务端反序列化到 POJO，失败重试或降级；关键字段校验。  
视频摘要、分镜、文章核心提取都走结构化，而不是自由散文难解析。

#### Q41：如何控制 LLM 成本与延迟？

**答：**  
并发槽位；能短则短的上下文（分层摘要而非整段硬塞）；模型分能力（chat/image/omni）；缓存相同请求；会员配额；异步任务避免占用 HTTP 线程硬等。

#### Q42：多模态和纯文本链路怎么选？

**答：**  
有口播的内容 ASR+文本 LLM 性价比高；PPT/无口播/画面信息重要时上 hybrid/omni。默认可用 audio-only 控成本，产品再放开 hybrid。

#### Q43：你对 Agent 的理解？

**答：**  
不是让模型为所欲为，而是 **LLM 决策 + 受限工具 + 权限与确认 + 可审计**。  
我做的是站内工具 Agent：查任务、创建任务需确认，强制用户隔离。

#### Q44：LangChain4j 在项目中解决什么？不解决什么？

**答：**  
解决：Chat 调用、部分结构化输出增强、统一供应商接入体验。  
不解决：也不该接管任务调度、TTS、Remotion、FLUX 协议细节——那些是业务与多媒体流水线。
