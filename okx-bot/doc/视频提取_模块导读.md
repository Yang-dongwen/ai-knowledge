# 视频提取 · 模块导读

**包：** `com.dwcode.okxbot.video`  
**入口：** `/api/v1/video/*`  
**前端：** `okx-trading-web` 视频提取页  
**对照代码，不是规划。**

更细的状态机 / 设计模式见 [视频提取_任务流程与设计模式.md](./视频提取_任务流程与设计模式.md)。本文只回答三件事：每个类干什么、核心请求怎么走、为什么拆成这样。

---

## 1. 这个模块在干什么

用户贴一条视频链接，后端在后台做完这些事（按模式可以少做几步）：

```
下载（yt-dlp + ffmpeg）
  → 转写（本地 Whisper）
  → 画面理解（可选：Omni 或抽帧）
  → LLM 总结
  → 文件进对象存储，临时目录清掉
```

HTTP **只接单、查单、暂停、重试、拿结果**。下载 / ASR / 多模态 / LLM 都不在请求线程里跑。

理解模式（`UnderstandingMode`）决定跑哪几步：

| 模式 | 下载 | Whisper | 画面 | LLM 总结 |
|------|------|---------|------|----------|
| `download_only` | ✓ | | | |
| `audio_only`（默认） | ✓ | ✓ | | ✓ |
| `hybrid` | ✓ | ✓ | ✓ | ✓（字幕摘要 + 画面融合） |
| `omni_only` | ✓ | | ✓ | ✓ |

## 2. 先建立一张图

```
浏览器
  POST /process          只写入 video_task = PENDING，立刻返回 taskId
  GET  /events           SSE 推状态
  GET  /tasks/{id}       详情 / 结果兜底

VideoProcessController        薄：参数进、ApiResult 出
        │
VideoProcessService           会员、并发上限、建任务、暂停/重试规则
        │
VideoTaskScheduler            全局最多约 2 个同时跑；PENDING 排队
        │
VideoTaskAsyncRunner          @Async 线程池
        │
VideoProcessingPipeline       按模式串步骤，步骤边界可暂停
        │
DownloadStep / TranscribeStep / UnderstandStep / SummarizeStep
        │
VideoDownloadService / TranscriptionService /
VideoUnderstandingService / SummarizationService
        │
yt-dlp · ffmpeg · Whisper HTTP · Omni/VLM · LlmChatClient
        │
StorageService → 对象存储（local / R2）
VideoTaskEventPublisher → SSE
```

读代码时记住：**Controller 不跑流水线；Pipeline 不拼 HTTP；Adapter 不写任务状态。**

## 3. 每个类做什么

DTO 全是请求/响应壳，下面不逐个展开。Mapper 是 MyBatis 表访问，也不展开。

### 3.1 入口与配置

| 类 | 做什么 |
|----|--------|
| `VideoProcessController` | REST + SSE。提交、列表、详情、暂停、重试、删除、转录/摘要、视频流、Cookie、模型列表。不写业务。 |
| `VideoProperties` | `video.*` 配置：工作目录、Whisper 地址、理解模式、时长软顶、每用户并发等。 |
| `VideoAsyncConfig` | 专用线程池 `videoTaskExecutor`（核心 2 / 最大 4）。和成片、文章任务池分开，避免互相堵。 |

### 3.2 任务生命周期

| 类 | 做什么 |
|----|--------|
| `VideoProcessService` | 对外业务入口。校验会员、每用户进行中上限、规范化 URL、选模型、insert PENDING、通知调度；查状态、暂停、重试（清空产物再入队）、删任务、Range 播视频、签发 media-url。 |
| `VideoTaskScheduler` | 槽位 + FIFO。`tryStartNext` 从 PENDING 拉任务；启动时把卡在运行态的任务标 FAILED（进程重启后内存槽是空的）。暂停标记也在这里。 |
| `TaskSlotKernel`（`common.task`） | 进程内「正在跑哪些 id / 谁被要求暂停」。每个模块自己 new 一份，视频和成片不抢同一组槽。 |
| `VideoTaskAsyncRunner` | 独立 Bean，`@Async` 调 Pipeline。单独成类是为了 Spring 代理生效，不能写在 Scheduler 里自己调自己。 |
| `VideoProcessingPipeline` | 流水线外壳：建 context、逐步执行、步骤后落库、SSE、失败清理、成功把 scratch 升到对象存储。按 `UnderstandingMode.stepsAfterDownload()` 决定跑哪些步。 |
| `OmniDurationGuard` | 视频太长时：拒绝，或把 hybrid 降成 audio_only。避免超长片打满 Omni 配额。 |
| `VideoTaskEventPublisher` | 把任务状态推到 `UserSseHub`（channel=`video`）。单机内存。 |
| `VideoTaskEntity` / `VideoTaskMapper` | 一张 `video_task` 表：状态、路径、模型、JSON 产物指针。 |
| `VideoTaskStatus` | PENDING → DOWNLOADING / TRANSCRIBING / UNDERSTANDING / SUMMARIZING → SUCCESS / FAILED / PAUSED。 |

### 3.3 流水线步骤（agent.step）

步骤类很薄：改状态文案、调对应 Service、把结果塞进 context。真正干活在 Service。

| 类 | 做什么 |
|----|--------|
| `VideoPipelineStep` | 步骤接口：`name` / 运行态 / 是否适用于当前模式 / `execute`。 |
| `VideoPipelineContext` | 一次 run 的内存上下文：任务、模式、下载结果、字幕、画面结果、暂停检查。 |
| `VideoTexts` | 步骤文案（「正在转录音频」之类）。 |
| `DownloadStep` | 调 `VideoDownloadService`。每种模式都跑。 |
| `TranscribeStep` | 调 Whisper。`audio_only` / `hybrid` 才跑。 |
| `UnderstandStep` | 调画面理解。`hybrid` / `omni_only` 才跑。 |
| `SummarizeStep` | 调 LLM 总结。`download_only` 不跑。 |

### 3.4 领域服务（一步一件事）

| 类 | 做什么 |
|----|--------|
| `VideoDownloadService` | 调 yt-dlp 下视频，ffmpeg 抽音频。处理「视频轨/音频轨没自动合并」的情况。 |
| `TranscriptionService` | 把音频路径交给 `WhisperClient`。自己不拼 HTTP。 |
| `VideoUnderstandingService` | 按时间窗切段 → 交给 Router → 聚合成整段画面结果。 |
| `MediaChunkPrepareService` | ffmpeg 把长视频切成能喂 Omni 的短片，并控制体积。 |
| `SummarizationService` | ASR 先压成 `TranscriptDigest`，再让 LLM 出 JSON 总结；hybrid 时和画面结果 Fuse。**禁止把全量字幕塞进 Fuse prompt。** |
| `StorageService` | 处理中用 scratch：`storage.scratch/video/{taskId}/`；成功后对象 key：`{env}/video/{userId}/{taskId}/...`。 |
| `VideoCookieService` | 把浏览器 Cookie 写成 Netscape `cookies.txt` 给 yt-dlp。**服务端全局一份**，不按用户隔离（本机下载器限制）。 |

### 3.5 出站：Port / Adapter / Client

| 类 | 做什么 |
|----|--------|
| `VideoUnderstandingPort` | 「给一段视频，还我画面理解结果」。Mock 走整段；Omni/抽帧走分片。 |
| `VideoUnderstandingCommand` / `VisualUnderstandingResult` | 入参 / 出参。 |
| `VideoUnderstandingProtocol` | 协议名常量：`mock` / `nvidia-omni-chat` / `frame-vlm` / `auto`。 |
| `VideoUnderstandingRouter` | 按 protocol 选 Adapter；Omni 媒体失败可回退抽帧。 |
| `NvidiaOmniVideoAdapter` | 调 NVIDIA 视频 Omni（整段短片进模型）。 |
| `FrameSampleVlmAdapter` | 抽帧 + 视觉模型，Omni 不可用时的退路。 |
| `MockVideoUnderstandingAdapter` | 不调真模型，方便本地通流水线。 |
| `WhisperClient` | HTTP 调本机 Whisper 微服务 `/v1/audio/transcriptions`。 |
| `WhisperProcessManager` | Spring 启动时拉起本地 Whisper 进程，关闭时杀掉。 |
| `LlmChatClient`（`common.ai`） | 总结用的文本 LLM。和成片/对话共用，不在 video 包里。 |
| `UnderstandingDegradedException` | 画面理解降级（例如 Omni 挂了走抽帧）时带给上层的信号。 |

### 3.6 工具

| 类 | 做什么 |
|----|--------|
| `ProcessExecutor` | 跑外部进程（yt-dlp / ffmpeg），超时、日志、杀掉。 |
| `VideoUrlNormalizer` | 把抖音/B 站等粘贴链接收成 yt-dlp 能认的地址。 |
| `MediaRangeSupport`（`common.web`） | 视频播放的 HTTP Range。 |

### 3.7 共用、本模块会碰到

| 类 | 和视频的关系 |
|----|----------------|
| `MemberStatusService` | 提交提取要有效会员。 |
| `AiModelConfigService` | 任务选哪个 chat / omni 模型，存在库里。 |
| `ObjectStoragePort` / `ScratchWorkspace` | 持久对象 vs 处理中临时目录。 |
| `MediaUrlService` | R2 预签名直链，播放不走应用服务器。 |
| `UserSseHub` | 按 userId 扇出 SSE。 |

## 4. 核心接口调用路径

### 4.1 提交提取（主路径）

`POST /api/v1/video/process`

```
Controller.process
  → VideoProcessService.submit
       校验会员、每用户进行中数量
       规范化 URL、解析 understandingMode、记下 LLM/Omni 模型
       insert video_task (PENDING)
       SSE：created
       VideoTaskScheduler.notifyPending
  → 立即返回 VideoTaskResponse（此时还没下载）

Scheduler.tryStartNext
  → 槽位有空 + DB 里还有 PENDING
  → VideoTaskAsyncRunner.runAsync(taskId)     // 换线程

Pipeline.run
  → DownloadStep → VideoDownloadService → yt-dlp/ffmpeg
  → （非 download_only）
        TranscribeStep → WhisperClient
        UnderstandStep → VideoUnderstandingService → Router → Omni 或抽帧
        SummarizeStep  → SummarizationService → LlmChatClient
  → 每步：改 status、写库、SSE
  → 成功：产物上传对象存储，清 scratch，status=SUCCESS，放槽，再 tryStartNext
  → 失败：FAILED + 错误信息，清临时文件
  → 暂停：步骤边界看到 pause 标记 → PAUSED，放槽
```

前端同时开着 `GET /api/v1/video/events` 收状态；列表接口只是兜底。

### 4.2 查结果 / 播视频

| 接口 | 路径 | 走到哪 |
|------|------|--------|
| 详情 | `GET /tasks/{id}` | `getStatus`，读库 + 必要时读摘要 JSON |
| 字幕 | `GET /tasks/{id}/transcription` | 读转录 JSON |
| 摘要 | `GET /tasks/{id}/summary` | 读摘要 JSON |
| 直链 | `GET /tasks/{id}/media-url` | `MediaUrlService` 预签名（优先） |
| 代理流 | `GET /tasks/{id}/video` | 应用服务器 Range 回退 |

### 4.3 暂停 / 重试 / 删除

```
暂停  POST /tasks/{id}/pause
  → 库状态改 PAUSED（排队中）或 requestPause（正在跑）
  → 正在跑的那步跑完检查点才真正停，不立刻杀 yt-dlp
  → 放槽，调度下一单

重试  POST /tasks/{id}/retry
  → 只允许 PAUSED / FAILED / SUCCESS
  → 清空产物，状态回到 PENDING，再 notifyPending
  → 不是从失败那一步接着跑

删除  DELETE /tasks/{id}
  → 校验归属，删库行 + 对象/scratch
```

### 4.4 画面理解（hybrid / omni_only 才进）

```
UnderstandStep
  → VideoUnderstandingService.understand
       按时长规划时间窗（短片一条、中等均分、长视频稀疏采样）
       MediaChunkPrepareService 切出短 mp4
       VideoUnderstandingRouter
            mock        → MockAdapter（整段假结果）
            nvidia-omni → NvidiaOmniVideoAdapter（每窗一次）
            失败可回退  → FrameSampleVlmAdapter
       拼成 VisualUnderstandingResult
  → 落 visual JSON，供 SummarizeStep Fuse
```

### 4.5 Cookie / 模型配置

和流水线无关，只是下载和选模型的配套：

- `GET/POST/DELETE /cookies` → `VideoCookieService`（yt-dlp 登录态）
- `GET /models`、`/model-configs*` → `AiModelConfigService`（超管测模型会真实扣额度）

## 5. 为什么这么设计

**HTTP 不跑重活。** 下载和 ASR 可能十几分钟。请求线程里做会超时、占满 Tomcat。所以「接单一张表 + 专用线程池」。

**槽位限制并发，而不是来一个就 @Async。** 机器上同时跑很多 yt-dlp/Whisper 会把 CPU/磁盘打满。全局大约 2 槽，再加每用户上限。槽在**进程内存**，DB 只存任务状态。

**步骤拆开，Pipeline 只编排。** 下载、转写、理解、总结失败原因完全不同，要能单独看日志、单独测、步骤边界暂停。模式不同只是跳过某些 Step，不必再写四套流水线。

**Adapter 换理解协议，业务不绑死 NVIDIA。** Omni 贵且有时长限制；抽帧更便宜；Mock 方便本地。Router 负责选和回退。总结始终走 `LlmChatClient`，和画面协议分开。

**scratch 与对象存储分开。** 处理中文件乱、可删；成功后再升到 `{env}/video/{userId}/{taskId}`。重启后运行中任务标 FAILED，是因为 scratch 可能半成品，内存槽也对不上。

**重试整管线，不断点续跑。** 半成品状态很难保证一致（音频在、字幕不在）。实现简单：清产物，从 PENDING 再来。暂停是协作式检查点，不是杀 OS 进程。

**SSE 而不是前端狂轮询。** 步骤分钟级，推送足够。Hub 在内存，两台实例会推不到，规模还用不上 Redis。

**Cookie 全局一份。** yt-dlp 读的是本机文件，不是按用户的浏览器配置。这是已知简化，不要讲成多租户 Cookie 仓。

## 6. 不要和这些搞混

| 容易混 | 实际 |
|--------|------|
| 本模块 vs `aigen`（AI 成片） | 提取是「别人的视频 → 文字要点」；成片是「提示词 → 自己渲染视频」 |
| 上传断点续传 | 那是知识库附件；视频提取是拉远程 URL |
| `GET .../video` 的 Range | 播放/下载续传，不是任务断点 |
| 「失败自动从转写接着跑」 | 当前重试是整单重来 |

## 7. 读代码顺序（建议）

1. `VideoProcessController` + `VideoProcessService.submit`  
2. `VideoTaskScheduler` + `VideoTaskAsyncRunner`  
3. `VideoProcessingPipeline` + 四个 Step  
4. 对应四个 Service  
5. 需要画面时再看 Router / Adapter  
6. `StorageService`、`VideoTaskEventPublisher`
